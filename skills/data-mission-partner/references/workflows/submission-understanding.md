# 지정 양식과 설계 이해

공식 제출 설명, 서비스 설계, 구현 이유를 작성·검토하거나 사용자가 직접 설명할 준비를 요청할 때 읽는다. 실제 시험의 모범답안이나 문항을 생성·복원하는 지침이 아니다. AI 허용 단계에서만 사용한다.

## 양식이 먼저

초기에 실제 제출 양식·샘플·필수 파일명·필드·분량·순서를 확인한다. 제공 양식을 새로운 보고서로 대체하거나 섹션을 추가해 형식을 깨지 않는다. 양식이 없으면 현재 요청에 필요한 전달물만 정한다. 읽을 수 없으면 파일/항목이 미확인이라고 밝히고 과제 해결은 확인 가능한 범위에서 계속한다.

양식의 각 항목에 어떤 근거가 필요한지 내부적으로 연결한다. 목표·선택은 합의할 때, 구현·검증은 실제 발생할 때 갱신한다. 미실행 기능을 완료형으로 미리 작성하지 않는다. 공식 설명이 충분하면 별도 구조 지도·요약 보고서를 중복 작성하지 않는다. 협업용 필드가 필요하면 양식 형식을 유지하고 기존 작업 메모의 짧은 절을 사용한다.

## 하나의 기능을 끝까지 추적

중요한 기능마다 다음을 현재 코드·문서에서 확인한다.

**사용자 행동/입력 → 검사 → 핵심 처리 → 저장/상태 변경 → 반환/화면/파일 → 예외 처리**

실제 파일과 핵심 함수 또는 현재 구성의 다른 실행 단위를 연결한다. 기술적 함수가 없는 문서·콘텐츠 과제면 자료·변환 규칙·구성 단계로 설명한다. 이름만 보고 역할을 짐작하지 않고 본문·호출 관계·실행 결과를 확인한다. 바뀌기 쉬운 줄 번호 암기보다 경로와 실제 역할을 사용한다.

설명에는 **왜 필요했나 / 다른 방법 대신 왜 골랐나 / 감수한 점 / 어떤 사례로 확인했나 / 무엇을 못 확인했나**를 포함한다. 코드의 모든 줄을 장황하게 해설하지 않는다.

## 설계와 기록을 실제 상태에 맞춘다

- 요구·실무자 답·AI 제안·사용자 결정·현재 코드·검사 결과는 서로 다른 근거다. 실무자가 모호하게 말한 것을 합의로 만들지 않는다.
- 현재 코드가 문서와 다르면 자동으로 어느 한쪽을 정답으로 삼지 않는다. 의도한 요구를 다시 확인해 구현을 고칠지 설명을 고칠지 판단한다. 단순히 문서를 코드에 맞춰 필수 요구를 낮추지 않는다.
- 생성과 검증, 부분 검사와 통합 검사, 서버 응답과 실제 버튼 조작, 역할별 화면과 접근 통제, 메모리 저장과 재시작 후 영속 보관을 구분한다.
- “최적·실시간·안전·완전 자동·확장 가능”은 구현과 근거가 있을 때만 쓴다. 미래 개선안을 현재 기능으로 설명하지 않는다.
- 코드·조건이 바뀌면 영향받는 양식 항목·검증 사례·설명도 갱신한다. 최종 설명이 어느 저장 상태를 기준으로 했는지 확인한다.

## 이해 확인은 별도

AI가 읽고 설명한 것과 사용자가 이해한 것은 다르다. 사용자가 요청했으면 이미 완성된 기능 한 개를 자기 말로 설명해 보도록 안내한다. “입력이 어떻게 결과로 바뀌고, 왜 이 기준을 골랐으며, 예외는 어떻게 처리되는가”를 실제 구현과 대조해 빠진 부분만 보완한다. 사용자의 답을 받기 전 이해 완료로 쓰지 않는다. 모든 기능에 퀴즈를 강제하거나 다음 승인된 작업을 멈추지 않는다.

자료에는 정형화된 답변 대본 대신 실제 설계와 검증 근거를 남긴다. 제출물과 실제 구현이 질문의 전제와 다를 때는 그 차이를 설명할 수 있어야 한다. 구현하지 않은 예외 처리는 현재 한계와 추가 개선안으로 구분한다.

## 최종 정리와 종료

필수 결과·지정 문서의 항목·현재 코드·실무자 판단 기록·검사 근거를 대조한다. 제출 양식은 제출물이지 별도 복습 메모로 대체할 수 없다. 문장·용어·경로·숫자를 한 번 다듬고 불필요한 확장을 멈춘다.

AI 금지 단계가 시작되면 실행·설명·답안·개요·첨삭 등 지원을 모든 관련 세션에서 중단한다. 전환 대기시간을 추가 AI 작업 시간으로 가정하지 않는다. 작성한 문서가 그 단계에서 열람 가능한지는 실제 규칙을 확인하며, 문서가 있다는 이유로 허용됐다고 말하지 않는다. 다른 세션을 직접 멈출 수 없다면 그 한계를 알린다.
