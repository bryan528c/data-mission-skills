# 오류 해결 — 같은 실패를 반복하지 않기

예상과 다른 값, 실행 실패, 저장·연결 문제에서 사용한다. 이미 원인이 분명한 작은 오류에 장황한 조사 절차를 강요하지 않는다.

1. **증상을 같은 조건으로 확인한다.** 실제 입력·명령·오류·예상 결과를 확인한다. 실행 권한이 없으면 그 한계를 밝히고 필요한 오류 정보만 요청한다.
2. **처음 달라지는 지점을 찾는다.** 입력 읽기, 규칙 적용, 계산, 저장, 표시 중 어디서 어긋나는지 좁힌다. 최근 변경과 환경도 확인한다. 관련 없는 로그를 통째로 출력하지 않는다.
3. **가장 유력한 원인부터 하나씩 확인한다.** 원인이 맞으면 달라질 결과를 예측하고 검사한다. 여러 설정과 파일을 한 번에 바꾸지 않는다. 두 번 같은 접근이 실패했고 새 근거가 없으면 다른 가설·더 작은 재현·단순한 대안을 선택한다.
4. **최소 범위를 고치고 원래 증상을 재검사한다.** 수정한 입력 사례와 영향받은 정상 사례를 확인한다. 오류를 숨기거나 테스트를 삭제해서 통과시키지 않는다. 무관한 정리·프레임워크 교체를 섞지 않는다.
5. **사용자에게 짧게 연결한다.** “어디가 왜 틀렸는지 → 무엇을 바꿨는지 → 어떤 실제 결과로 확인했는지”를 설명한다. 미해결이면 필수 결과에 주는 영향과 추천 대안을 알린다.

반복 실패나 긴 대기가 생기면 승인 대기·정상 실행·실제 오류를 구분한다. 무조건 같은 요청을 다시 보내거나 모델 강도부터 높이지 않는다. 남은 시간을 알 때만 조사 여유를 판단한다. 필수 기준을 몰래 낮추지 않는다.

웹 미리보기는 서버 실행 상태·로그 → 실제 포트 → 허용된 바인딩·경로 → 로컬 응답 순서로 점검한다. HTTP 응답 성공과 화면에서 버튼이 실제로 작동한 것은 다르다. 자동 화면 조작이 금지된 환경이면 사용자가 확인할 조작과 기대 결과만 짧게 안내한다.

플랫폼·감독 오류는 발생 시각(확인된 경우), 단계, 직전 동작, 오류 문구를 정리해 공식 신고 경로를 안내한다. 관리 프로세스·보안 설정을 바꾸거나 제한을 우회하지 않는다. 다른 안전한 작업이 있으면 이어간다.
