# 오류 해결과 작업 복귀

실행이 실패하거나 계산·파일·화면 결과가 예상과 다를 때 읽는다. 고칠 코드부터 추측하지 말고 실패한 동작과 입력을 확인한다.

1. 실제 오류 문구, 입력, 직전 변경을 확인하고 실패를 재현할 수 있는 작은 실행을 찾는다. 기존 검사나 실제 입력을 우선 사용한다.
2. 정상인 경우와 실패한 경우의 차이를 좁힌다. 원인 가설마다 “맞다면 무엇이 관찰되어야 하는가”를 정하고 하나씩 확인한다.
3. 근거가 생기면 필요한 부분을 수정한다. 관계없는 구조 변경·라이브러리 교체·여러 설정 변경을 함께 넣지 않는다.
4. 처음 실패한 입력을 다시 실행하고 영향받는 기존 기능도 확인한다. 출력 숫자를 직접 바꾸거나 검사 기준을 낮추어 통과시키지 않는다.
5. 사용자가 이해할 원인, 수정 위치, 실제 재실행 결과, 남은 한계를 전달하고 다음 작업으로 복귀한다.

같은 시도가 실패했고 새 근거가 없다면 반복하지 않는다. 입력·경로·환경·업무 규칙 중 아직 확인하지 않은 쪽을 조사한다. 필요한 정보가 없으면 오류 문구나 재현 입력처럼 막힘을 풀 한 가지를 요청하고 독립 작업은 계속한다.

남은 시간에 비해 조사가 길어지면 확인한 사실과 대안의 결과 차이를 설명한다. 우회나 범위 축소가 필수 요구를 바꾸면 사용자 판단을 받는다. 실패한 필수 항목을 완료로 바꾸지 않는다.

## 환경 문제를 구분한다

프로그램이 계속 실행 중인지, 입력/권한을 기다리는지, 실행 오류인지, 플랫폼 자체 장애인지 구분한다. 미리보기가 안 열리면 실행 상태·실제 포트·플랫폼 요구 주소·경로·허용된 응답 확인을 차례로 살핀다. HTTP 응답 성공과 화면 버튼의 실제 동작은 구분한다. 화면 자동화나 외부 연결은 실제 환경이 허용하는 방식만 사용한다.

도구 제한으로 직접 확인할 수 없는 부분은 그 범위를 명시한다. 관찰하지 않은 버튼·로그·실행 성공을 꾸미지 않는다. 제공 환경을 업데이트하거나 제한을 우회하는 것을 일반 오류 수정으로 취급하지 않는다.

플랫폼 장애는 확인된 발생 시각, 단계, 직전 동작, 오류 문구를 정리해 실제 공식 신고 경로를 안내한다. 신고 전송 자체의 권한은 별도로 확인하며, 관리 프로세스나 보안 설정을 임의로 바꾸지 않는다.
