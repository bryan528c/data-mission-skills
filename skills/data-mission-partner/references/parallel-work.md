# 병렬 작업 — 역할보다 파일과 결과를 나눈다

사용자가 여러 Codex 세션을 쓰겠다고 했거나 독립 작업 분리를 요청했을 때만 읽는다. 스킬이 터미널을 자동으로 생성·조작하거나 서로의 대화를 전송하는 기능은 없다. 같은 파일을 읽는 것과 같은 문맥을 가진 것은 다르다.

## 시작할 때 한 번

- 현재 세션이 총괄 A, 독립 구현 B, 검토 C 중 무엇인지 실제 요청으로 확인한다. 지정이 없고 필요하면 한 번만 물으며, 한 세션이면 역할 문서 없이 진행한다.
- 실제 프로젝트 루트, 적용 지침 경로, 제공 양식, 현재 파일 상태를 확인한다. 같은 파일을 보는지 확인되지 않은 다른 세션이 파일을 공유한다고 가정하지 않는다.
- 과제·기존 아키텍처를 분업하기 위해 재구성하지 않는다. 별도 Worktree나 Git 브랜치는 이미 준비돼 있고 통합 방법을 아는 경우만 선택한다.
- 일반적인 출발점은 A+B와 필요시 읽기 검토 C다. 숫자는 권장안이며 제한도 자동 생성 지시도 아니다. 실행 자원·동시 호출 지연·통합 비용을 보고 줄인다.

## 누구의 일인가

| 역할 | 맡는 결과 | 바꾸지 않는 것 |
| --- | --- | --- |
| A | 공통 업무 기준·인터페이스·핵심 처리·통합·지정 설명 문서 | 사용자 판단을 대신 확정하거나 진행 중인 B 파일을 덮어쓰기 |
| B | 배정된 파일의 독립 기능과 그 기능의 실제 확인 | 공통 설정·API·DB 구조·다른 담당 파일을 독단적으로 변경 |
| C | 실제 파일과 요구를 대조한 오류·불일치·미확인 근거 | 제품 코드 변경. 보고 파일을 쓸 경우 그 파일만 별도 소유 |

모델 이름이 역할을 결정하지 않는다. 실제 허용 모델과 관측한 결과로 선택한다. 같은 결과물을 두 세션이 동시에 만드는 경쟁 작업은 기본으로 하지 않는다.

## 위임에 필요한 최소 약속

공통 기준이 있는 문서를 우선 사용한다. 없고 병렬화가 필요할 때만 짧은 공통 메모를 만든다. **목표 / 확정 입력·출력 / 담당 파일 / 완료 확인 / 기준 버전**을 기록하며 A만 갱신한다. 문서명을 정답처럼 강제하지 않는다.

B는 배정 파일과 자기 인계 기록만 쓴다. 공통 약속을 바꿀 필요가 생기면 이유와 필요한 변경을 전달하고 영향받지 않는 작업을 계속한다. A가 바꾼 기준은 관련 B 작업 시작·완료 시 다시 읽힌다. 작성됐다고 상대가 이미 읽었다고 가정하지 않고, 사용자가 짧게 읽기 요청을 전달한다. 반복 폴링·자동 호출 서버는 만들지 않는다.

## 코드 외에 겹치는 자원도 조심한다

한 파일에 한 작성자가 원칙이다. 같은 DB·출력 파일·서버 포트·의존성 잠금 파일·Git index도 공유 자원이다. 패키지 설치, 공통 설정·DB 마이그레이션, Git 변경 작업은 합의한 한 담당자로 모은다. 테스트는 가능한 임시 출력·시험 DB를 사용해 현재 결과를 덮지 않는다.

B가 작업을 마쳤다는 사실과 A가 소유권을 인수했다는 사실을 구분한다. **B 쓰기 중지 → 변경 파일·현재 기준·검증·한계 인계 → A가 실제 파일 대조 → 통합 검증** 순서로 넘긴다. 아직 수정 중이면 그 범위만 통합을 미룬다.

Git을 쓰더라도 문서·브랜치·공유 폴더가 충돌을 자동 해결하지 않는다. 커밋은 허용되고 요청된 경우만, 다른 작성자가 관련 파일을 안정화한 뒤 실제 지정 파일을 검토해 수행한다. `git add -A`, 강제 reset·checkout·push로 다른 작업을 지우거나 몰래 포함하지 않는다. 로컬 기록을 서버 장애의 백업 보장으로 표현하지 않는다.

## UI를 맡길 때

A와 사용자가 **주 사용자·주요 행동·필수 정보·입출력·금지할 불필요 요소**를 정한다. B는 이를 구현하며 빈 상태·로딩·잘못된 입력·실패·성공을 구분한다. 첫 핵심 화면이 렌더링되면 초기에 확인하되, 간격이나 작은 수정마다 승인받지 않는다. 과제에 없는 카드·메뉴·통계·애니메이션을 자율적으로 늘리지 않는다.

실제 API가 아직 준비되지 않아 임시 데이터를 썼다면 눈에 보이게 표시하고 인계에 적는다. 최종 실제 데이터 연결을 검증하기 전 기능 완료로 보고하지 않는다. 디자인 시연과 실제 저장·권한 구현은 다르다.

## 인계는 곧 설명 근거

자기 인계에는 **변경 파일과 핵심 함수 / 입력→처리→출력 / 사용한 규칙과 이유 / 실행한 확인 / 미확인 / 다음 담당이 할 일**만 적는다. 대화 전문·내부 추론을 옮기거나 사용자 결정으로 꾸미지 않는다. 기존 지정 문서에 같은 내용을 다시 쓰기보다 A가 필요한 사실만 반영한다.

공통 기준이 바뀌면 이전 결과와 검사 중 무엇이 영향받는지 표시한다. C의 보고는 읽은 파일 버전/상태를 밝혀, 이후 변경된 코드를 과거 검사로 통과시킨 것으로 쓰지 않는다.

짧은 사용자 문장: “B는 최신 공통 기준을 읽고 담당 범위만 이어가.” / “A는 B의 인계와 실제 파일을 대조해 통합해.” 이 문장은 해당 세션에서 실행해야 하며, 다른 창으로 자동 전달되지 않는다.
