# 식단 편성과 메뉴 관심

일반 업무 지침이다. 특정 영양·의료 기준이나 법적 의무를 임의로 확정하지 않는다.

## 먼저 이해할 말

**식단 편성**은 날짜·식사·장소에 메뉴를 배치하는 일이다. **관심 지표**는 조회·좋아요·선호 응답 등 측정한 행동이며 실제 섭취량이나 전체 직원의 선호와 같지 않다. 응답자만의 결과와 전체를 구분한다.

## 확인할 질문과 자료

운영일·휴일·식사 시간·지점, 메뉴와 레시피 ID, 예산 단위, 제공량·조리 가능량, 반복 제한 등 실제 조건을 확인한다. 관심 데이터의 대상·기간·중복 행동과 어떤 의사결정에 사용할지도 확인한다. 알레르기·식재료 정보는 제공된 권위 있는 원자료와 갱신 상태를 따른다.

## 작은 첫 결과와 분업

하루 또는 한 주의 **메뉴 선택 → 실제 제약 검사 → 식단 조회/수정**을 먼저 연결하고 요구된 기간으로 확장한다. A는 편성·지표·조건 검사, B는 달력/목록·메뉴 상세·수정·관심 표시를 맡을 수 있다. 달력과 차트를 둘 다 만드는 것은 필수가 아니다.

## 놓치기 쉬운 검사

- 월 길이·요일·휴일·식사별 중복과 누락을 확인한다. 날짜를 바꾸면 메뉴 연결이 올바른지 본다.
- 1인분 비용·총비용·수량을 섞지 않는다. 근거 없는 영양값이나 조리량을 생성하지 않는다.
- 메뉴 관심의 반복 클릭·유일 응답자·분모를 확인한다. 조회수 높은 메뉴를 더 건강하거나 안전하다고 판단하지 않는다.
- 성분·알레르기 정보가 없으면 “없음/안전”이 아니라 **정보 미확인**이다. 사용자에게 실제 원자료 확인 필요를 보여준다.
- 재료 대체·레시피 변경 후 비용과 관련 성분 표시를 다시 검토한다. 메뉴 이름만 같다고 정보가 유지된다고 가정하지 않는다.
- 운영자 수정 화면, 일반 조회, 저장·내보내기 값이 같고 실제 권한 구현 범위를 정확히 설명한다.

## 한 사례로 설명

가상으로 응답자20명 중15명이 메뉴A를 선택했다면 응답자 내 선호는75%다. 전체100명 중75명이 선호한다고 말할 수 없다. 한 사람이 여러 번 누른20건이라면 응답자 수20명인지부터 확인해야 한다.

## 설명 준비

왜 그 날짜에 배치했는지, 관심값을 어떤 단위로 셌는지, 충족하지 못한 편성 조건과 정보 미확인을 어떻게 표시하는지 설명한다. 실제 사용자 영양 개선을 측정 없이 주장하지 않는다.

공개 배경: [FSA 성분 정보가 불확실한 경우의 안내](https://www.food.gov.uk/business-guidance/allergen-information-for-non-prepacked-foods-best-practice-voluntary-information). 정보 정확성 관점의 참고이며 한국 과제의 법규·의료 기준으로 적용하지 않는다.

## 심화 실무: 데이터 모델·구현·검증

**입력·상태 설계:** 운영 지점·날짜·식사 슬롯·휴일, 메뉴/레시피 버전, 공급·제공량·원가, 실제 편성 규칙, 선호 이벤트(행동 종류·기간·이벤트 수·고유 인원·노출 수)를 분리한다. 레시피가 바뀌면 같은 메뉴명이어도 재료·표시값이 달라질 수 있다.

**작동하는 첫 결과:** 운영 가능한 날짜·식사 슬롯 생성 → 메뉴 후보와 제약 확인 → 며칠치 기본 편성 → 반복·비용·공급 검사 → 조회/수정 → 실제 요구된 월간 범위 확대. 선호 분석은 독립 집계해 의사결정의 근거로만 연결한다. A는 조건·집계·검사, B는 달력/표·수정·경고 표시를 맡는다.

**계산·판단 규칙:** 조회·좋아요·설문 응답을 실제 섭취량 또는 전체 인원의 선호로 바꾸지 않는다. 한 사람의 다중 반응, 분모·노출량 차이를 고려한다. 안전 정보가 없으면 알레르기 없음·안전으로 표시하지 않는다. 비용은 1인분·제공량·운영기간 단위가 일치할 때 계산한다.

**검증 시나리오:** 2월/윤년, 비영업일, 동일 날짜·식사 중복, 빠진 슬롯, 금지 반복 간격, 제공량·예산 경계, 재료 정보 미확인, 고유 사용자 1명의 다중 클릭, 메뉴 변경 뒤 비용·정보·내보내기의 갱신.

**설명용 가상 사례:** 가상 메뉴 A는 100회 노출에 20회 반응, B는 20회 노출에 15회 반응이면 반응수는 A가 크지만 노출 대비 반응률은 A 20%, B 75%다. 어느 지표가 적합한지는 실제 업무 목적에 달렸다.

**실무자 상호작용과 서술형 대비:** 편성 가능 조건, 선호 자료의 의미와 분모, 계획 생성·수정·재검사, 정보 누락 처리, 누구의 최종 결정인지 실제 코드와 문서에 연결한다.

### 단계별로 실제 작업을 끊어 진행하기

① 월별 실제 운영 슬롯을 만든다. ② 해당 날짜/식사에 배치 가능한 메뉴를 가린다. ③ 메뉴 중복·예산·공급·실제 제공된 안전 기준을 검사한다. ④ 관심 지표는 별도 집계해 편성 판단 근거로 붙인다. ⑤ 운영자 수정 뒤 조건과 상세 데이터를 재검증한다.

### 구현 상태·데이터 연결 계약

슬롯 ID·메뉴 ID·레시피 버전·편성 상태·근거를 보존한다. 좋아요 수와 실제 수요를 같은 필드에 넣지 않는다. 월간 일정 저장과 실제 배식·조리 지시는 별개로 취급한다.

### 합격 판정 대신 실제로 확인할 것

없는 날짜, 휴일, 동일 메뉴의 금지된 반복, 원가 단위 변경, 미확인 성분, 중복 클릭에 의한 지표 부풀림을 검증한다. 모든 슬롯을 채웠어도 필수 제약 위반이 있으면 성공으로 표시하지 않는다.

### 업무 담당자에게 제안할 질문 방향

참여 데이터가 적으면 '선호는 참고로만 둘지, 편성에 필수 반영할지'를 확인하고 응답률과 미응답의 한계를 밝힌다.
