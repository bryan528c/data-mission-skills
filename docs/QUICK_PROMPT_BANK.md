# 최종 상황별 작업 프롬프트

일반적인 업무·프로그램 제작을 위한 준비 자료. 실제 문제·답안·개인 정보는 포함하지 않는다.
스킬의 예시와 예상은 점검 후보일 뿐 실제 요구가 아니다. 실제 지시서·데이터·지정 양식·최신 운영 규칙이 우선이다.

## 사용하는 방법

- 처음에는 A에서 01, 방향에 동의하면 A에서 02, 업무가 배정되면 B에서 03을 사용한다. 나머지는 해당 상황에만 사용한다. 모두 순서대로 실행하지 않는다.
- 파일을 읽힌 뒤에는 해당 세션에 “이 파일의 16번 적용해”처럼 요청해도 된다. 번호 자체가 Codex 명령은 아니며 파일을 읽을 수 있어야 한다.
- 이 파일을 편집기에서 여는 것만으로 AI가 읽거나 실행하지 않는다. 첫 요청에 실제 파일명을 말하고 읽게 한다. 내용을 붙여넣거나 파일만 저장한 뒤 자동 실행을 기다리지 않는다.
- 실제 과제 위치·스킬 위치·공통 기준·인계 경로는 확인한 뒤 재사용한다. 파일 위치가 확인되지 않으면 짐작하지 않는다. 다른 세션의 대화·실무자 DM은 자동 공유되지 않는다.
- 터미널에서 긴 붙여넣기가 안 되면 허용된 편집기에 저장한 이 파일을 읽히고 번호만 직접 입력한다. 붙여넣기·업로드 자체가 제한돼 있다면 우회하지 말고 허용된 공개 저장소 가져오기 방식을 사용한다.
- 스킬은 https://github.com/bryan528c/data-mission-skills 이다. 이미 받은 완전한 사본을 우선 사용한다. 같은 이름을 여러 번 설치하거나 작업 중 계속 최신 버전으로 바꾸지 않는다.
- 짧은 질문에는 답부터 한다. 이미 승인한 작업은 계속하고, 중요한 업무 기준·범위·위험을 바꿀 때만 확인한다. 자료를 읽기 전 사용자에게 기술 선택을 떠넘기지 않는다.
- 이 파일과 스킬은 안전장치나 자동 잠금 프로그램이 아니다. 다른 터미널의 실제 중지·동기화는 확인해야 한다.

## 01. A 시작 — 실제 과제 파악과 첫 방향 제안

너는 총괄 Codex A야. 먼저 실제 과제 폴더의 지시서·제공 데이터·기존 코드·지정 제출 양식을 확인해. 준비 키트의 README를 과제 지시서로 착각하지 마. 공개 bryan528c/data-mission-skills가 이미 있으면 경로·버전을 확인하고 START_HERE.md와 필요한 지침만 읽어. 없다면 허용된 별도 위치에 가져와. 기존 파일을 덮거나 설치·MCP 설정부터 하지 마.

예상 업무·사진·예시·스킬을 이번 과제의 필수 요구로 취급하지 마. 실제 근거로 목표, 필수 결과, 미확정 조건, 추천하는 첫 작업과 확인 방법을 짧게 정리해. 공식 문서·실무자 확인·AI 제안·내 결정·미확인을 구분해. 아직 제품 구현은 시작하지 말고 중요한 방향을 먼저 함께 정하자. 이미 승인된 작업을 이어받은 경우에는 처음부터 다시 계획하지 마.

## 02. A — 방향 승인, 실행 시작과 B 분업

지금 제안한 방향으로 진행해. 승인된 범위의 구현·실행·검증은 사소한 단계마다 기다리지 말고 이어가. 첫 결과는 실제 입력에서 실제 출력까지 연결해.

B가 독립 완료할 작업이 있으면 결과물, 수정 가능한 실제 경로, 입력·출력과 오류 형식, 완료·검증 조건, 기준 버전을 정해 기존 작업 메모에 기록해. 적절한 메모가 없을 때만 짧은 공통 기준 파일 하나를 만들고 경로를 알려줘. 공통 설정·설치·DB·출력·포트·Git 변경 담당도 하나로 정해. B용 지시 한 문장에 실제 기준 파일 경로를 넣어줘. 독립 작업이 없으면 억지로 분리하지 마. 지정 양식은 실제 수행 내용이 생길 때 갱신해.

## 03. B 시작 — 배정된 범위만 구현

너는 독립 구현 Codex B야. 실제 작업 폴더·읽을 스킬·A의 공통 기준 파일을 확인해. A의 대화와 실무자 DM을 자동으로 안다고 가정하지 마. 이미 가져온 지침을 읽고 재설치하지 마. 담당 결과·수정 경로·입출력·검증 기준이 기록돼 있으면 그 범위로 실행해. 기준 파일을 찾지 못하거나 담당이 비어 있으면 필요한 경로/배정만 물어보고 임의로 구현하지 마.

네 파일과 네 인계 기록만 수정해. 공통 규칙·설정·DB·Git·다른 담당 파일 변경은 요청으로 남겨. UI 담당이면 합의한 사용자 행동과 정보 구조를 구현하고 불필요한 기능을 추가하지 마. 결과는 실제 실행해 확인하고, 변경 파일·핵심 함수·기준 버전·검증·한계·다음 통합 작업을 인계해. 다른 세션으로 자동 전달했다고 주장하지 마.

## 04. C 시작 — 선택적 독립 검토

너는 검토 Codex C야. 실제 과제·공통 기준·현재 결과를 읽고 필수 누락, 로직 오류, 지정 설명과 코드의 불일치를 찾아줘. 제품 파일·공통 기준·공유 DB는 수정하지 마. 실행 검사는 부작용 없는 명령 또는 허용된 임시 데이터에서만 해. 보고 파일이 필요하면 네 파일 하나만 사용해. 치명도, 실제 경로·근거, 재현 입력, 기대/실제 결과, 수정 제안을 중요도순으로 알려줘. 확인한 코드 상태를 남기고 읽기 검토를 실제 실행 검증이라고 부르지 마.

## 05. 사전 예상과 실제 과제가 다르다 — A

사전 주제나 예시에 맞추지 말고 실제 지시서·자료·양식으로 요구를 다시 대조해. 무엇이 확인된 필수이고 무엇이 예상·선택 기능인지 구분해. 맞는 기존 작업은 보존하고, 잘못 가정한 부분의 영향만 정리해. 새 구현 방향을 추천하되 전체 프로젝트를 폐기하거나 전면 재작성하지 마. 업무 유형 지침도 필요한 것만 다시 골라.

## 06. 계획·설명만 반복하고 실제 작업이 안 된다 — 해당 세션

이미 승인된 방향과 현재 파일부터 확인하고, 다음 작동 결과를 만드는 구현·실행·검증으로 넘어가. 계획서·요약을 다시 만드는 것으로 대신하지 마. 실제로 막힌 것이 승인, 자료, 오류, 다른 담당자의 결과 중 무엇인지 구분하고 막힌 부분만 알려줘. 중요한 결정이 더 필요하지 않다면 다음 승인을 기다리지 마. 단, 배정되지 않은 파일은 건드리지 마.

## 07. 실무자에게 무엇을 물을지 준비 — A

원문·데이터·실행에서 이미 알 수 있는 답부터 확인해. 결과를 바꾸는 미확정 조건 중 가장 중요한 것부터, 왜 필요한지와 답에 따라 무엇이 달라지는지를 붙여 바로 보낼 질문으로 정리해. 가능한 선택지와 추천안이 있으면 짧게 제시해. 목표·예외·우선순위를 구체화하되 질문 수를 채우거나 점수를 위해 추가 요구를 만들어내지 마. 내가 실제 메신저에서 보낼 것이니 자동 발송하지 마.

## 08. 실무자 답이 모호하거나 대답하지 않는다 — A

내가 전달한 실제 답변에서 확정 사실·의견·미응답을 나눠줘. 같은 질문을 반복하기보다 구체적인 사례·선택지로 재확인이 필요한지 판단해. 확답 없이도 진행 가능한 가역적 선택은 추천 기준·영향·한계를 제시하고, 중요한 업무 가정은 내 선택을 받은 뒤 적용해. 확인되지 않은 규칙을 실무자 승인으로 쓰지 마. 원본 훼손·권한 변경 등 위험한 행동은 보류하고 영향 없는 작업은 계속해. 답변 원문을 전달받지 못했다면 내용을 지어내지 마.

## 09. 실무자 답변·요구·내 결정이 바뀌었다 — A

방금 전달한 변경을 원문과 기존 합의에 대조해. 서로 충돌하면 출처·적용 대상·시점을 표시하고 우선순위를 임의 확정하지 마. 채택된 변경은 영향받는 코드·데이터 계약·검사·지정 양식만 갱신해. 공통 기준 버전을 바꾸고 B가 다시 읽어야 할 정확한 경로와 변경점을 알려줘. 기존 검증 중 무효가 된 부분을 표시하고, 영향 없는 작업은 유지해.

## 10. B에게 최신 기준 반영

A의 공통 기준 파일을 다시 읽고 내가 전달한 변경에 영향받는 담당 부분만 반영해. 이전 기준과 달라진 입력·출력·상태·예외를 확인해. 공통 파일을 직접 바꾸지 말고 필요한 요청을 인계에 남겨. 적용한 기준 버전과 실제 검증 결과를 적어줘. 파일이 바뀌었다는 이유로 상대 세션도 이미 읽었다고 가정하지 마.

## 11. B 작업을 마치고 인계

현재 맡은 단위를 안정화하고 실제 변경 파일·핵심 함수, 입력→처리→결과, 사용한 기준 버전, 실행한 검사와 결과, 미검증·통합 주의를 기존 인계에 갱신해. 미완료가 있어도 숨기지 마. 인계 상태를 '이 범위 쓰기 종료, A 인수 확인 대기'로 남기고 해당 파일의 추가 수정을 멈춰. 새 역할을 받기 전 A 영역으로 넘어가지 마. 오래된 인계를 새 완료로 재사용하지 않도록 상태를 명확히 해.

## 12. A가 B 결과를 통합

B 인계와 실제 파일을 함께 읽어. 해당 범위 쓰기 종료가 명시됐거나 내가 확인했는지 보고, 알 수 없으면 그 확인만 요청해. 현재 계약과 다른 부분·누락·임시 데이터를 찾아줘. 인수가 확인된 범위만 통합하고, 사용자 입력부터 계산·저장·표시·내보내기 중 실제 요구된 경로를 검증해. 단위 검사 성공을 통합 성공으로 바꾸지 마. 지정 설명에는 확인한 결과만 반영해.

## 13. 같은 파일·설정·DB를 동시에 고친 것 같다 — A

충돌 가능 범위의 쓰기부터 조정해. 내가 다른 담당 세션에도 중지를 전달할 수 있게 대상과 이유를 알려줘. 다른 세션을 실제로 멈추지 못했다면 멈췄다고 말하지 마. 현재 디스크 파일, diff, 확인 가능한 미저장 변경·인계를 비교해 보존할 내용을 정해. 마지막 저장을 정답으로 삼거나 reset·clean·강제 덮어쓰기로 해결하지 마. 합의된 한 담당자가 해당 범위만 병합하고 영향받는 검사·설명을 갱신해.

## 14. UI를 처음 구현한다 — UI 담당

실제 사용자·가장 중요한 행동·필수 입력/결과·오류/빈 상태와 데이터 연결 규칙을 기준으로 최소 화면을 만들어. 과제에 없는 카드·차트·메뉴·애니메이션·새 프레임워크를 늘리지 마. 첫 핵심 화면을 일찍 확인할 수 있게 하고, 정확한 포트·경로·조작·기대 결과를 알려줘. 임시 데이터라면 명시해. 큰 정보 구조가 아직 합의되지 않았다면 나머지 화면 확장은 보류하되 독립적인 승인 작업은 진행해.

## 15. UI가 어지럽거나 내 의도와 다르다 — UI 담당

실제 필수 기능과 유지할 장점부터 확인해. 사용자의 핵심 행동이 바로 보이도록 정보 우선순위·용어·배치를 정리하고 중복·장식만 줄여. 기능을 몰래 삭제하거나 전체 디자인을 새로 만들지 마. 로딩·빈 결과·잘못된 입력·실패·구버전 결과를 실제로 필요한 범위에서 구분해. 수정 뒤 입력→처리→결과 흐름을 확인하고, 직접 보지 못한 화면은 검증했다고 하지 마.

## 16. 오류가 나거나 같은 수정이 반복된다 — 담당 세션

실제 오류·입력·기대 결과와 최근 변경을 확인하고 작은 조건으로 재현해. 어디서 처음 어긋나는지 좁혀 가장 유력한 원인을 하나씩 검사해. 새 근거 없는 같은 수정과 여러 설정의 동시 변경을 반복하지 마. 원인이 확인된 최소 범위를 고친 뒤 원래 실패 입력과 영향받는 정상 사례를 재실행해. 시험 기준을 낮추거나 출력을 손으로 고쳐 성공 처리하지 마. 권한 밖 파일 수정은 담당자에게 넘겨.

## 17. 느리거나 멈춘 것 같다 — 해당 세션

현재 상태를 승인 대기·모델 응답 대기·파일 탐색·테스트/빌드·서버 실행·자원 부족·플랫폼 오류로 구분해. 직접 확인할 수 없는 지연 원인은 추정으로 표시해. 이미 돌고 있는 작업을 중복 실행하지 말고 현재 수정·실행 상태를 보존해. 반복 탐색·긴 로그·관련 없는 전체 검사를 줄이고, 독립적으로 진행할 작업과 조정할 우선순위를 제안해. 모델·Fast·설정·프로세스를 임의 변경하지 마. 모든 세션이 느리면 세션을 더 늘리지 말고 플랫폼 안내와 신고를 고려해.

## 18. 연결 복구·새 세션·모델 전환 후 이어가기

역할, 실제 폴더, 적용 스킬, 현재 공통 기준, 진행 중인 다른 담당 작업, 실제 저장 파일·검증·남은 일을 확인해 이어가. 기억하지 못한 대화는 기록과 현재 파일로 확인하고 과거 완료를 추측하지 마. 진행 중인 쓰기·서버를 함부로 중단하거나 새 프로젝트를 만들지 마. 중요한 실무자 답·사용자 선택·실제 경로는 기존 메모에 짧게 보존해. 세션/모델 변경은 별도 실행 여부와 허용을 확인하고, 이 요청만으로 환경을 업데이트하지 마.

## 19. 자료가 없거나 파일·스킬·도구를 읽지 못한다 — A

정확히 부족한 것이 파일 자체, 추출된 본문, 누락된 열, 업무 기준, 권한, 설치 실패 중 무엇인지 확인해. 표본을 읽은 것과 전체를 읽은 것을 구분해. 기존 제공 도구로 가능한 작은 방법을 먼저 시도하고, 누락을 0·정상·승인으로 채우지 마. 필요한 정보만 한 번 구체적으로 요청하고 영향 없는 작업은 진행해. 스킬 등록에 막히면 완전한 원본을 직접 읽어 적용해. 외부 AI 키·업로드·제한 우회로 해결하지 마. AI 런타임이 없으면 정적 응답을 실제 AI로 속이지 마.

## 20. Browser 미리보기가 열리지 않거나 실행이 안 된다 — 실행 담당

실제 실행 명령·작업 폴더·로그·서버 상태·포트·허용된 바인딩·경로를 순서대로 확인해. 같은 서버를 계속 중복 실행하거나 무관한 프로세스를 종료하지 마. 제공 Browser에서 내가 넣을 실제 포트/경로와 조작을 알려줘. 서버 응답 성공과 실제 화면·버튼 동작은 구분해. 자동 화면 조작이 금지된 환경에서는 우회하지 말고 내가 직접 볼 항목만 안내해. 플랫폼 장애면 확인된 증상·발생 단계와 신고할 내용을 정리해.

## 21. 구현이 맞는지 실제로 검증 — A 또는 담당자

필수 요구를 현재 구현과 연결하고 결과를 바꿀 위험부터 검사해. 정상·경계·누락/중복/잘못된 입력·조건 충돌·수정/재계산·저장 실패 중 관련 사례를 선택해. 기대값은 원문 규칙과 독립 계산으로 정하고 실제 결과·명령·범위를 남겨. 임시 데이터로 시연한 것과 실제 데이터 처리를 구분해. 검사 0건·건너뜀·미실행을 통과라고 하지 마. 결과가 화면·저장·내보내기·지정 설명에서 같은 기준인지 확인해. 공유 데이터에 영향을 주는 검사는 담당과 조정해.

## 22. 추가 기능·새 도구를 넣을지 판단 — A

이 추가가 실제로 어떤 사용자 문제를 줄이는지, 필수 요구·검증이 끝났는지, 구현·통합·설명 비용과 남은 시간에 맞는지 비교해. 만들기·단순 대안·이번 제외 중 추천과 이유를 제시하고 아직 구현하지 마. 가점 추정 때문에 기능을 늘리지 마. 실무자에게 확인할 가치가 있으면 구체적 제안으로 정리해. 추가 승인 후에만 범위를 바꾸고, 공개 자료라도 라이선스·권한·외부 전송을 확인해.

## 23. 구조를 내가 이해할 수 있게 설명 — A 또는 담당자

현재 구현된 중요한 기능 하나를 실제 파일과 호출 흐름으로 설명해. 목적 → 입력 → 검사 → 핵심 처리 → 저장/상태 → 응답/표시 → 예외를 연결하고, 핵심 함수의 입력·출력·역할과 이 구조를 고른 이유를 알려줘. 낯선 말은 쉬운 뜻과 현재 사례로 먼저 풀어줘. 파일명만 보고 추측하거나 모든 코드 줄을 해설하지 마. 문서형 결과라면 없는 함수 대신 자료·구성·검증 흐름을 설명해. 미구현 제안과 현재 동작을 구분해.

## 24. 지정 양식 작성·갱신 — A

실제 양식의 원본 필드·순서·분량·파일명·저장 위치를 먼저 확인하고 그대로 작성해. 필요하면 원본 템플릿과 제출 파일을 구별해. 요구/실무자 답/내 결정 → 구현 위치 → 실제 동작 → 검증 → 한계를 항목에 맞게 연결해. AI 제안·AI 구현·내 판단·내 관찰을 섞지 마. 문서와 코드가 다르면 의도한 요구부터 확인해 고칠 쪽을 판단하고, 문서만 낮춰 필수 미구현을 숨기지 마. 독립 메모로 공식 양식을 대체하지 마. 비공개 작업 기록은 공개 저장소로 보내지 마.

## 25. 직접 설명 연습 — AI 허용 작업 단계에서만

현재 제출물의 실제 구조와 결정 근거를 이해하는 연습을 하자. 중요한 기능/설계 선택/예외 처리 중 하나를 물어보고 정답부터 말하지 마. 내 답을 받은 뒤 실제 코드·기록과 다른 부분만 짚어줘. 막히면 빠진 기초 개념과 한 사례부터 설명해. 실제 후속 문항을 안다고 하거나 암기용 답안을 만들지 마. 이 세션은 내 답을 기다려도 되지만 다른 세션의 독립 구현까지 멈추라고 하지 마. 내 답 없이 이해 완료라고 기록하지 마.

## 26. 구현·지정 문서·실무자 기록 최종 대조 — A

새 기능을 만들지 말고 지정 문서의 중요한 주장을 실제 코드·데이터·검증 기록에 대조해. 최적·실시간·자동·안전·권한·영구 저장 등 표현이 실제로 증명되는지 확인해. 필수 요구가 부족하면 문구를 바꾸기만 하지 말고 결함과 영향을 알려줘. 설명용 예와 실제 결과, 단위 검사와 전체 동작을 구분해. 정확성을 맞춘 뒤 용어·숫자·경로·읽는 순서만 한 번 다듬고 불필요한 반복 검토는 끝내.

## 27. 시간이 부족하다 — A

내가 알려준 남은 시간 또는 실제 확인한 타이머를 기준으로 필수 작동 실패, 저장·제출 위험, 지정 문서 누락부터 처리해. 선택 기능·새 도구·전면 재설계는 중단해. 즉시 수정할 것, 안전한 단순화에 내 동의가 필요한 것, 한계로 남길 것을 짧게 구분해. 필수 기준을 몰래 낮추지 마. B는 현재 단위를 안정화해 인계하도록 내가 전달할 요청을 알려줘. 통합·문서 대조·내 제출 확인에 필요한 시간을 남겨. 타이머를 못 보면 시간을 지어내지 마.

## 28. 제출 직전 — AI 허용 단계에서 A

새 개발·새 위임을 멈추고 각 담당의 쓰기 종료 상태부터 확인해. 다른 세션을 직접 중지할 수 없으면 내가 해야 할 행동을 알려줘. 실제 필수 파일·형식·경로·저장 상태·실행·핵심 검증·지정 양식 일치·제출 용량을 확인해. 원본이나 필요한 결과를 임의 삭제하지 마. 준비 완료와 제출 완료를 구분하고 최종 제출 버튼·완료 표시 확인은 내가 직접 할게. 제출 확정 전에 내가 핵심 구조·판단·한계를 설명할 수 있게 필요한 사실만 짚어줘. 확정 후 질문 대기를 추가 AI 작업 시간으로 잡지 마.

## 29. 검증한 상태를 로컬 Git으로 기록 — Git 담당자만

현재 과제에 실제 Git 저장소가 있는지, 다른 담당자의 쓰기가 끝났는지 확인해. 관련 변경 경로·diff와 검사 범위를 검토해 이번에 승인된 변경만 로컬 커밋해. 다른 사람의 미완료 변경을 함께 담거나 git add -A·강제 reset·clean·Push를 하지 마. Git이 없으면 지금은 파일 저장과 실제 상태 메모만 남겨. 커밋을 플랫폼 제출 또는 장애 후 복원 보장이라고 표현하지 마.

## 30. AI 금지 단계 전환 — 사람이 실행할 안내, AI 프롬프트 아님

제출을 확정하기 전에 A·B·C의 과제 작업이 끝났는지 확인한다. 각 Codex의 상태를 보고 응답 중단·종료를 실제로 확인한다. AI 금지 단계가 시작되면 이 파일의 요청을 보내지 않는다. 답안·초안·개요·설명·첨삭을 어떤 세션이나 외부 AI에도 요청하지 않는다. 이미 만들어둔 메모의 열람 허용 여부도 임의로 가정하지 않는다. 서버·감독·플랫폼 관리 프로세스를 AI 세션과 혼동해 종료하지 않는다. 제출·질문 전환 오류는 공식 안내·문의 절차를 따른다.

## 평가 대응에 관한 공통 태도

필수 요구와 실제 작동을 우선한다. 실무자의 모호한 요구는 실제 사례로 구체화하고, 중요한 판단은 내가 한다. AI 제안의 오류를 근거로 수정하되 평가용 거절·오류·대화를 연출하지 않는다. 추가 기능은 사용자 가치와 시간으로 선택한다. 지정 양식·실제 코드·검증·내 설명을 일치시킨다. 커뮤니티의 고득점 조언은 공식 배점·합격 보장이 아니다.
